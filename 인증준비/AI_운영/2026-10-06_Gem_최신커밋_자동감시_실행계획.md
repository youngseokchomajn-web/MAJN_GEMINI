# MAJN_GEMINI — Gemini Gem 최신 커밋 자동 감시·실행 계획

- 작성일: 2026-10-06
- 상태: PLAN / 구현 전
- 목적: GitHub 최신 커밋을 감지하고 Gemini Gem이 변경사항을 읽어 필요한 검토·검증·후속작업을 자동으로 수행하는 구조를 만든다.

## 1. 최종 목표

GitHub 새 커밋 → 변경 감지 → 영역 분류 → Gem 실행 → 최신 HEAD/SSOT 확인 → 검증 → Evidence 기록 → 다음 작업 생성 → 필요 시 Draft PR → 사용자 승인 → merge.

핵심은 '커밋마다 무조건 수정하는 봇'이 아니라 최신 상태를 읽고 다음 작업을 판단하는 Engineering Agent다.

GitHub Actions는 push, path filter, workflow_dispatch, schedule 등의 트리거를 지원하므로 감시 계층으로 사용한다.

## 2. 기존 MAJN 규칙 유지

- GitHub가 Source of Truth.
- CLAUDE.md, parallel-tracks.md, .agents/AGENTS.md 우선 확인.
- track별 파일 소유권 유지.
- git add -A / git add . 금지.
- EasyEDA Bridge는 track-pcb 독점.
- 실제 PCB를 확인하지 않고 PCB 수정 확정 금지.
- 데이터시트/실측/권위 DRC 없이 정격·극성·연결성을 단정하지 않음.
- 문제 → 가설 → 검증 → 실패 → 수정 → 재검증 → 결정 기록.
- 자동화가 최종 merge/push를 독단적으로 수행하지 않음.

## 3. 전체 구조

GitHub commit
→ GitHub Actions watcher
→ changed-files 추출
→ Change Classifier
→ Gem Job Queue
→ Gemini Gem
→ GitHub / EasyEDA / 실제 HW evidence
→ Decision
→ Draft PR
→ 사용자 승인
→ merge

EasyEDA/실제 HW 접근은 GitHub-hosted runner에서 무리하게 수행하지 않고 현재 PC의 EasyEDA Pro + API Gateway + Bridge 구조와 track-pcb 소유권을 따른다.

## 4. 감시 단계

1차는 main push + 수동 실행으로 시작한다.

watch 대상:
- main
- 이후 필요성이 확인된 개발 브랜치

변경 영역:
- PCB: 인증준비/pcb, 인증준비/mcp_development, .agents/skills/easyeda-api, eda_routing_rules.md, pcb_comps.json
- Firmware: 인증준비/firmware
- AI: Majn_AI_Workspace
- Cert/EMC: 인증준비 하위 문서
- Biz: 사업계획서, 경쟁제품조사, 프라이머 배치 지원
- 운영: CLAUDE.md, parallel-tracks.md, .agents/AGENTS.md

운영 규칙 변경은 HIGH PRIORITY / MANUAL REVIEW.

## 5. Change Classifier

입력:
- base SHA
- head SHA
- commit message
- changed files
- branch
- actor

출력 예:
{
  "areas": ["emc", "pcb"],
  "risk": "high",
  "requires_gem": true,
  "requires_physical_access": true,
  "auto_modify_allowed": false
}

위험도:
- LOW: 단순 문서/오탈자
- MEDIUM: 일반 코드/문서
- HIGH: PCB, 전원, EMC, firmware-hardware interface, SSOT
- CRITICAL: PCB geometry, 전원부, 부품, 핀맵, 인증판단, 운영규칙

CRITICAL은 자동 분석 가능하지만 자동 설계 변경은 금지한다.

## 6. Gem 실행 전 Context Loading

Gem은 실행될 때 반드시 다음을 최신 HEAD에서 읽는다.

1. 현재 commit SHA
2. trigger commit
3. 변경 파일
4. CLAUDE.md
5. parallel-tracks.md
6. .agents/AGENTS.md
7. 해당 track 문서
8. 최신 decision log
9. 관련 SSOT
10. 기존 실패/검증 기록

대화 기억만으로 이전 상태를 가정하지 않는다.

## 7. Gem 기본 알고리즘

START
→ 현재 HEAD 확인
→ 직전 처리 상태 확인
→ 변경 파일 추출
→ 영역 분류
→ 관련 SSOT 탐색
→ 기존 결정/실패 기록 탐색
→ 영향 여부 판단
→ 검증 계획 생성
→ 실행 가능한 검증 수행
→ Evidence 저장
→ 판정
→ 후속 작업 생성
→ 필요 시 Draft PR

## 8. 판정 상태

모든 task는 다음 중 하나로 종료한다.

NO_ACTION
OBSERVE
DATA_REQUIRED
BLOCKED
EXPERIMENT
FIX_REQUIRED
VERIFICATION_REQUIRED
APPROVE
REJECT
CONVERGED

애매한 결과를 단순히 '완료'로 기록하지 않는다.

## 9. Evidence 형식

각 실행은 최소 다음을 남긴다.

- Task ID
- Trigger commit
- Current HEAD
- Changed files
- Relevant SSOT
- Question
- Hypothesis
- Evidence
- Verification method
- Result
- Risk
- Decision
- Remaining actions
- Physical-access requirement
- Human-approval requirement

예:
EMC-001 / trigger SHA / 질문 / SSOT / 실제 확인값 / 판정 / 다음 행동.

## 10. 작업 큐

권장 구조:

.gem/
- config.yml
- queue.yml
- policies.md
- prompts/system.md
- prompts/pcb.md
- prompts/emc.md
- prompts/firmware.md
- prompts/cert.md
- prompts/biz.md
- runs/YYYY-MM-DD/

queue는 task ID, area, trigger SHA, priority, status, dependency, physical-access requirement, approval requirement를 가진다.

실행 상태는 가능하면 Actions artifact/log 또는 별도 상태 저장소를 사용한다. 매 실행마다 state 파일을 commit하면 watcher가 자기 commit을 다시 감지하는 무한루프가 생길 수 있기 때문이다.

## 11. 중복 실행 방지

고유키:
repository + commit SHA + task type

이미 처리된 경우 SKIP_DUPLICATE.

## 12. 무한루프 방지

Gem이 결과 문서를 commit하더라도 다시 자기 자신을 처리하지 않는다.

방법:
- bot-generated commit 식별
- [gem-auto] prefix 사용
- watcher에서 자동결과 commit 제외
- 결과는 가능하면 Draft PR branch에 기록
- 동일 run chain 추적

## 13. 자동 수정 정책

자동 허용:
- 분석 결과 문서
- 검증 결과
- TODO/queue
- 테스트 결과
- Draft PR

사용자 승인 필요:
- PCB 수정
- 회로 수정
- BOM 변경
- 부품 변경
- firmware 동작 변경
- 인증 판단 변경
- 운영규칙 변경
- main merge

절대 자동 금지:
- PCB fabrication 최종 변경
- EasyEDA Cloud master 직접 변경
- 인증 적합 판정 확정
- 실측하지 않은 값을 실측값으로 기록
- 실패한 검증을 통과로 변경

## 14. EasyEDA 정책

현재 repo에 이미 EasyEDA Pro bridge/API 경로가 있으므로 새 API를 만들지 않는다.

EasyEDA Pro → API Gateway → Bridge :49620 → 검증된 API 순서.

이 연결은 track-pcb 소유로 유지한다.

자동화 단계:
A. GitHub → Gem → 문서 분석
B. 사용자 PC에서 EasyEDA bridge 연결
C. 실제 PCB read-only 검증
D. 사용자 승인 후 PCB 변경

## 15. EMC를 첫 자동화 대상으로 선정

현재 MAJN의 실제 작업과 직접 연결되는 영역이다.

EMC trigger:
- 인증준비 문서
- mcp_design_flow.json
- PCB export
- BOM
- PnP
- netlist
- EMC decision log

자동 검토 순서:
1. 최신 EMC session log
2. Action List
3. risk assessment
4. SSOT
5. PCB export
6. 이전 geometry evidence
7. 현재 변경점

현재 P0:
L1 / D3 / U3 / C5 / BOOST_SW

P1:
PVDD_12V / C6 / C7 / U4 / AMP_OUT_A± / AMP_OUT_B± / J1 / J2

P2:
USB-C / ESP32 RF / FB1~FB4 / GND stitching / cable common-mode

## 16. EMC 자동 실행 예

mcp_design_flow.json이 변경되면:

1. diff 확인
2. 부품/좌표/핀맵 변경 확인
3. 기존 EMC 위험도 확인
4. 기존 BOOST loop evidence 확인
5. 새 상태 비교
6. 위험도 변화 판단
7. 필요한 검증 task 생성
8. 결과 기록
9. 수정 필요 시 Draft PR

단순히 '파일이 변경됨'으로 끝내지 않는다.

## 17. Firmware 자동 검토

Firmware 변경 시:
- hardware interface 확인
- pin map 확인
- power/AMP/IMU/BLE 영향 확인
- hardware SSOT 비교
- build/test
- 실제 장치 검증 필요 여부 표시

실제 장치 검증이 불가능하면 PHYSICAL_VERIFICATION_REQUIRED.

## 18. 인증 자동 검토

인증 변경 시:
Requirement → Evidence → Gap → Required Test → Human/Professional Review.

자동화는 compliance claim을 확정하지 않는다.

## 19. Draft PR 정책

Gem이 실제 수정 필요성을 판단하면 Draft PR을 만든다.

PR 본문:
- trigger commit
- 변경 이유
- evidence
- 검증 결과
- 예상 위험
- 변경 파일
- 사용자 확인사항
- merge 전 조건

자동 merge 금지.

## 20. 실패 처리

실패도 결과로 기록한다.

예:
RUN_FAILED
- EasyEDA bridge unavailable
- required file missing
- API unavailable
- test failed
- ambiguous SSOT

상태는 BLOCKED 또는 DATA_REQUIRED로 남기고 다음 관련 commit에서 재평가한다.

## 21. 보안

API key가 필요할 경우:
- repository secret 사용
- 로그에 secret 출력 금지
- prompt에 key 삽입 금지
- 외부 PR 자동 실행 제한
- 최소 권한
- main write 보호

첫 단계는 read/analyze 중심으로 시작한다.

## 22. 구현 단계

### Phase 0 — 정책
산출물:
- .gem/config.yml
- .gem/policies.md
- .gem/prompts/system.md

완료:
- 기존 CLAUDE/parallel-tracks와 충돌 없음.

### Phase 1 — Commit Watcher
산출물:
- .github/workflows/gem-watch.yml
- changed-file classifier

완료:
- main push 감지
- SHA 확인
- changed files 추출
- 영역 분류
- 중복 방지

이 단계에서는 Gem write 권한을 주지 않는다.

### Phase 2 — Read-only Gem
commit → watcher → Gem → analysis → report가 재현 가능해야 한다.

### Phase 3 — Task Queue
- 중복 task 제거
- blocked task 유지
- 완료 task 추적
- 새 commit에서 재평가

### Phase 4 — Draft PR
문서/테스트/분석 스크립트/decision log 중심.
PCB master 변경과 main merge는 금지.

### Phase 5 — EasyEDA read integration
current PCB snapshot, components, nets, coordinates, tracks/vias, geometry evidence를 확보.

### Phase 6 — EMC 자동 검토
첫 미션:
L1/D3/U3/C5 → BOOST_SW → current loop → GND return → SSOT comparison.

### Phase 7 — 제한적 자동 수정
문서/테스트/비위험 metadata부터 허용.
PCB/전원/firmware 핵심 변경은 계속 승인형.

## 23. 검증 시나리오

Test 1: 일반 문서 commit → NO_ACTION 또는 LOW
Test 2: EMC 문서 commit → EMC task 생성
Test 3: mcp_design_flow.json 변경 → HIGH + SSOT review
Test 4: PCB export 변경 → PCB/EMC review
Test 5: Gem 결과 commit → duplicate/loop 방지
Test 6: EasyEDA bridge unavailable → BLOCKED + PHYSICAL_VERIFICATION_REQUIRED
Test 7: Gem 분석 실패 → RUN_FAILED + task 유지

## 24. 성공 기준

- 최신 commit SHA 정확 인식
- 변경 파일 정확 분류
- 관련 SSOT 자동 탐색
- 기존 결정로그 확인
- 동일 task 중복 방지
- Evidence 포함
- 실패를 성공으로 위장하지 않음
- 물리검증 필요 여부 표시
- PCB 자동수정 금지
- main 자동 merge 금지
- track ownership 위반 없음

## 25. 바로 다음 구현 작업

한 번에 전체를 만들지 않는다.

1. .gem/config.yml
2. .gem/policies.md
3. .gem/prompts/system.md
4. .github/workflows/gem-watch.yml
5. changed-file classifier

위 5개를 read-only로 먼저 안정화한다.

그 다음:
watcher → read-only Gem → queue → Draft PR → EasyEDA read → EMC 자동검토 → 제한적 자동수정 순서로 진행한다.

## 26. 최종 운영 모델

사용자 작업
→ GitHub commit
→ Gem 자동 감지
→ 최신 상태 읽기
→ 영향 분석
→ 기존 결정/실패 기록 확인
→ 검증
→ 다음 작업 자동 생성
→ 필요하면 Draft PR
→ 사용자 확인
→ merge
→ 다시 감시

최종 목표는 Gem을 '한 번 시키면 한 번 답하는 AI'가 아니라 **MAJN 개발 상태를 계속 따라가면서 다음 검증 작업을 이어가는 Engineering Agent**로 만드는 것이다.

자동화의 범위보다 검증 가능성을 먼저 확보한다.
